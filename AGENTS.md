## Sevic Reach
- Subdirectories may have their own AGENTS.md; read it before changing files there.
- Backlog membership and first-send promotion are enforced by database triggers; Backlog uses Outreach drafting and sequence scope so existing approvals, recipient schedules and history survive promotion.
- Funnel reporting uses paginated, narrow browser-client reads and pure aggregations over message logs and both sequence tables; ownership and recorded-sender attribution stay separate to avoid misleading team totals.
- Named contacts are stored in firm_contacts; sequence channel recipient IDs select those contacts or a reserved primary-contact ID, and sequence_deliveries tracks each destination independently so retries cannot resend successful or unresolved attempts.
- New named-contact schedules use contact_sequence_messages and contact_sequence_deliveries; draft context includes designation, and scheduling/reply stopping is scoped to that contact. Legacy firm sequences stay intact to preserve sent history.
- Lead qualification and the research fit verdict (fit_score/fit_max/fit_tier, copied by a trigger from the firm's newest brief) live on firms separately from stage; unclassified values stay NULL so existing firms are never arbitrarily labelled.
- Migration SQL regex avoids inline `(?i)` flags and `?` quantifiers (use the regexp_match flags argument, `{0,1}`) — the SQL transport mangles `?` into silent no-matches.
- Signed-in pages use src/routes/_authenticated and browser-client RLS (`is_team_member`). Shared route error recovery also covers caught lazy-import failures, preventing blank pages.
- Roles live in `user_roles` (first sign-up becomes admin via trigger) — avoids privilege escalation via profiles.
- Follow-up tasks and stage "reached_*" timestamps are generated by database triggers on firm stage changes — keeps cadence logic in one place regardless of client.
- WhatsApp sends go through a server function using Gupshup secrets; delivery status and replies arrive via /api/public/gupshup-webhook which only updates known message ids and known firm phones — keeps credentials server-side.
- Manual and scheduled WhatsApp sends share whatsapp.server.ts: use approved template variables outside each recipient's 24-hour inbound window, retain free text inside it, and store the rendered outgoing content — keeps transport and message history consistent.
- Bulk email goes through Zoho Mail (ZOHO_* secrets, region defaults to zoho.in) via src/lib/zoho.server.ts, history in email_messages — secrets stay server-side; Send stays disabled until secrets exist.
- Lead enrichment runs in src/lib/research.functions.ts through src/lib/firecrawl.server.ts, whose transport must match the linked Firecrawl connection's mode (currently direct API on api.firecrawl.dev, not the connector gateway), then AI writes a structured brief saved to firm_research — keeps keys server-side and briefs reusable.
- Geography filters use firms.city and firms.state, filled at import, never free-text notes — editing notes must not alter segmentation.
- Custom filters are team-shared lists in firm_lists + firm_list_members (cascade on delete) — membership is explicit, independent of stage/geography columns.
- Team accounts are created only by admins through server functions using the admin client; public sign-up is disabled in auth settings — prevents strangers from joining the workspace.
- Per-stage saved messages live in stage_templates (one row per stage) and are filled client-side with {{name}}/{{studio}} — same placeholders as bulk email.
- Every email/WhatsApp row records the firm's stage at insert time via a DB trigger; email replies are pulled from the Zoho inbox on demand (checkEmailReplies) and stored as direction 'in' rows deduped by provider_message_id — no Zoho webhook needed.
- AI message drafts, firm/contact sequences and redrafts use an offer-first chain with separate feature reference, offer guidance and tone files; the offer transport contract lives in the server-only assembler and research prompts stay independent, because bundled assets replace runtime filesystem reads.
- Recoverable prompt parsing/coverage failures produce conservative drafts without disclaimer UI or acknowledgement gates; provider/auth failures remain terminal and stored channel references retain fit and WhatsApp eligibility safeguards, because drafting recovery must not authorise sending.
- Message generation uses one server-only native Anthropic streaming helper with schema validation, separate from the research-brief provider — model changes cover single drafts, firm/contact sequences and redrafts without changing enrichment or exposing credentials.
- WhatsApp-specific writing guidance and research-grounded recovery live in a shared drafting module; permission remains separate from copy generation so ineligible channels do not degrade to empty or generic drafts.
- WhatsApp approval and send review use current firm consent to override stale AI eligibility flags; transport consent, recipient validation and reply stopping remain independent because AI output is not a permission source.
- Per-lead stage follow-up sequences live in sequence_messages (cadence in src/lib/sequences.ts); email and WhatsApp are approved and sent independently (email_status/whatsapp_status; status is a summary); approved channels are sent by an hourly pg_cron call to /api/public/hooks/send-sequences, each row claimed once — the route only sends already-approved, due messages so stray calls can't send extra.
- Optional sales persona notes live per stage in firm_personas (firm_id, stage unique); drafts use all saved stage notes when available without requiring them — firms.persona is deprecated.
- Campaigns (campaigns + campaign_firms) advance one bounded phase (research → draft → send) per firm per tick under a per-campaign DB lease, via the every-minute /api/public/hooks/campaign-tick schedule and an in-app runner; sends reuse sequence_messages approval and the shared sequence sender, so consent, reply-stop and delivery logs stay identical to manual follow-ups.
